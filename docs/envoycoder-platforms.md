# macOS, Windows and Linux

**Code:** `packages/platform` · **Rule:** no `process.platform` checks in feature code.

---

## 1. Why this is a package

EnvoyCoder drives *other people's CLI programs* on three operating systems. Each of those facts
multiplies: how you find a binary on `PATH`, how you quote an argument, how you kill a process
*tree*, whether signals exist at all, and whether a pseudo-terminal is available.

Every function in `@envoycoder/platform` takes the platform as a parameter (defaulted to the real
one), so **the Windows branch is exercised on macOS** by the test suite. That is not a stylistic
preference: the EnvoyMesh codebase paid for the alternative twice in one afternoon — a lock that
assumed `ps` and `/proc`, and a shell snippet that assumed `setsid` (which does not exist on macOS),
each hiding inside logic that looked portable.

`PLATFORM_MATRIX` states what each OS supports, and a test asserts it covers exactly the platforms we
claim to ship for — a claim with no entry is a claim that silently does nothing there.

## 2. The matrix

| | macOS | Linux | Windows |
|---|---|---|---|
| Shipped | ✓ dmg, app | ✓ AppImage, deb, rpm | ✓ msi, nsis |
| Shell for a command line | `/bin/sh -lc` | `/bin/sh -lc` | `cmd.exe /d /s /c` (PowerShell on request) |
| Real signals | ✓ | ✓ | **no** — `kill` is terminate |
| Process-tree kill | process group (`-pid`) | process group | `taskkill /pid N /T [/F]` |
| Pseudo-terminal | posix-pty | posix-pty | **ConPTY** (Windows 10 1809+) |
| Symlinks without elevation | ✓ | ✓ | **no** — Developer Mode or elevation |
| `ssh` client | ✓ | ✓ | optional Windows feature |
| `PATH` delimiter | `:` | `:` | `;` |
| Executable suffixes | — | — | `.exe`, `.cmd`, `.bat`, `.ps1` (plus `PATHEXT`) |

## 3. The traps, written down

Each of these is a real failure mode, most of them already paid for by a sibling project.

**Finding a binary.** `spawn("claude")` works on macOS and fails on Windows, because the file is
`claude.cmd` and Node does not apply `PATHEXT` without a shell. `findBinary()` resolves the real path
with the platform's suffixes, and *that* is why the whole catalogue's CLI integration works on two
thirds of our platforms. (Paseo hit the same wall in its PTY path: ConPTY's `CreateProcess` ignores
`PATHEXT`, so a bare `claude` killed the terminal worker — `packages/server/src/terminal/terminal.ts:331-337`.)

**Which `PATH` to search at all.** The trap that is not about syntax but about *environment*, and the one
that produced the wrong word on screen: a process started by a **GUI** launch does not inherit the user's
shell environment. Measured on the machine this was written on — `launchctl getenv PATH` prints nothing, and
Finder-launched processes carry no `PATH` at all — so `~/.local/bin/claude`, `~/.npm-global/bin/codex` and
`~/.local/bin/cursor-agent` were all invisible to the Tauri-spawned daemon while being plainly installed.
Worse, the same daemon started from a terminal (the `npm run tauri:dev` arrangement) *did* see them, so two
launches of one product disagreed about what was on the machine. `path-discovery.ts` resolves a list a login
shell would recognise — the shell's own answer first, with a timeout and a marker so an rc file's chatter
cannot be mistaken for a `PATH`, then the daemon's own environment, then the well-known tool directories on
this platform — and both the probe and the spawn use that one list, because a binary that probes as present
and then cannot be started is worse than one reported missing. Nothing to repair on Windows: the registry
`PATH` *is* delivered to GUI processes there.

**Joining paths.** `path.join` uses the *host's* separator. Resolving `C:\tools` + `claude.cmd` on
macOS produced `C:\tools/claude.cmd` — a path Windows cannot find, generated by code that only ever
runs *for* Windows. `joinFor(platform, …)` exists for that, and the test that caught it runs on
macOS.

**Quoting.** POSIX and `cmd.exe` are different languages. `quoteForShell` **refuses** an argument
containing `%` or `!` on Windows rather than mangling it: those expand, and a silently corrupted path
becomes a bug report about the agent rather than about quoting.

**Killing a tree.** An agent spawns build tools, test runners and language servers. Killing the
leader leaves orphans holding file locks — on Windows, that means the next run cannot rewrite the
file it just wrote. `spawnTreeOptions()` puts the child in its own process group on POSIX, and
`buildKillPlan()` returns either a signal for the group or a `taskkill /T` argv, as a *plan* so it can
be logged and tested without killing anything.

**Windows signals.** There are none. `SIGTERM` and `SIGKILL` both become `TerminateProcess`, so a
cancelled run is terminated rather than asked to stop. `platformRefusal("signals", "windows")` says
so in words a user can read, instead of pretending the graceful path ran.

**File modes.** `chmod 0600` is a POSIX property. On Windows a file inherits the user's profile ACL,
and siblings that "set 0600" there are asserting nothing (Paseo's `applyPrivateMode` is an explicit
no-op on win32; DeepSeek Harness skips credential `chmod` there too). Consequence for us, stated in
`host-bridge` where the secrets live: **on Windows the protection is the issued session, not the file
mode** — so do not build a security claim on a mode bit.

**`fs.watch({recursive: true})` is forbidden on Linux.** Node 22 emulates it by watching every file
and it exhausts resources (Paseo's `docs/file-observation.md`). Our file observation will use one
watch per directory on Linux, and a native recursive watcher on macOS/Windows.

**Login-shell environment.** Inheriting a login shell's environment is a POSIX idea; Paseo's
implementation throws on Windows and keeps Electron's inherited env there. Our daemon inherits its
environment and reads configuration from files, which sidesteps the whole class.

## 4. DeepSeek Harness, per platform

Its own support matrix, which we rely on when driving it:

| | macOS | Linux | Windows |
|---|---|---|---|
| Shell | `bash -c` (persistent terminal uses `/bin/bash`) | `bash -c` | **`pwsh`** — resolved from `%ProgramFiles%\PowerShell\7`, then PATH, then PowerShell 5.1 |
| Sandbox | Seatbelt | `bwrap` → Landlock | ACL restricted token — **enforcement is `partial`** by design |
| No usable sandbox | fails closed (`SANDBOX_UNAVAILABLE`) | same | same |
| Signals | SIGTERM then SIGKILL | same | Windows skips straight to forced termination |
| Process tree | POSIX group / systemd scope | same | `taskkill /T`, ConPTY outside Job containment |
| Credential file mode | 0600 | 0600 | **skipped** |
| Windows symlinks | — | — | need Developer Mode |

Two consequences for us: on Windows the agent needs **`pwsh`** present (we should probe for it the
way we probe for the agent itself), and an escalation that cannot be answered is denied — which is
precisely why we drive its `acp` profile.

## 5. The desktop shell

Tauri v2, not Electron — the family already ships Tauri and its supervisor lessons are written against
it (`apps/tauri/src-tauri/src/main.rs` in EnvoyMesh). The cost, accepted: three WebViews (WKWebView,
WebView2, WebKitGTK) and therefore three rendering engines to sanity-check, which is why the UI uses
plain CSS custom properties and no exotic features.

What the shell owns, and why (`apps/desktop/src-tauri/src/main.rs`):

1. **Kill only the child you started.** Resolving "who is on port 4770" and killing them is how a
   supervisor kills another app's process.
2. **A health check must identify the node.** `{"ok":true}` proves a server exists, not that it is
   ours — two products sharing one transport is the family's normal situation.
3. **The shared home is resolved, never guessed** — `ENVOYMESH_HOME` → per-OS default → legacy
   adoption, so both apps agree where state lives.

Linux needs `libwebkit2gtk-4.1-0` and a FUSE provider for the AppImage; the bundle config declares the
first, and the second is a packaging check the roadmap owes (Paseo never validates it in CI, and its
AppImage hit exactly that gap).

## 6. Packaging and CI

* **CI runs all three OSes** (`.github/workflows/ci.yml`): peers check, typecheck, unit tests, the UI
  bundle, the smoke script, plus a Flutter job for the phone. The Windows and Linux legs are the
  point — they are where platform assumptions fail.
* **Windows signing is configured from the start.** Paseo ships unsigned NSIS builds and its Windows
  CI never launches the packaged app; we treat "installs and starts on Windows" as a milestone
  (M6), not a hope.
* **Icons** are generated (`npx tauri icon <png>`); this scaffold ships the config and leaves the icon
  set to that command rather than committing a placeholder that would have to be replaced.
